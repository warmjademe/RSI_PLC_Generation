# Haiku 输出格式失败诊断

结论：当前结果混合了中转接口不执行结构约束、提示词传递行为不一致、以及本地把辅助说明格式与 PLC 正确性绑定的问题。不能把格式失败直接解释为 PLC 逻辑能力不足，也不能用这轮早期结果评价历史经验机制是否有效。此次只排查和单独复测，没有修改正式实验协议、成绩或运行中的源代码。

## 1. 审计范围与数量

以 2026-09-17 09:00:27 的快照为界，逐项读取 216 个候选的逻辑请求、真实 HTTP 请求 JSON、SSE 原始事件、组装响应、候选记录和 token 回执。模型仍为用户指定的 TeamRouter `.cn` Haiku 接口。全部完整响应均可由原始 SSE 精确重建；请求中的 system、用户任务和 schema 均与逻辑记录一致。

| 结果 | 候选数 | 解释 |
|---|---:|---|
| 通过格式检查、进入 PLC 工具 | 60 | 不等于 PLC 测试成功 |
| 非规定 JSON 的代码或分析文本 | 100 | 含直接 ST、多个程序版本、分析或片段 |
| 唯一含代码 JSON 块，但块外有说明 | 10 | 现有解析器要求整个响应是一个 JSON 对象或单一 JSON 围栏 |
| JSON 可解析，但辅助说明超长 | 45 | change_summary 超限 35，applicability_notes 超限 10；按首个拒绝字段计数 |
| 流式网络中断、无完整响应 | 1 | 单列，不与模型格式违约混算 |

155/216（71.8%）个候选因格式被拒，均未进入 PLC 测试。这 155 次全部有完整 `end_turn`，不是 max_tokens 截断；合计消耗 2,513,747 个接口上报 token。token 统计包含代理上报的缓存读写，不代表独立核验的上游计费。

## 2. 中转接口确实未执行结构约束

客户端发送 `output_config.format`，结构要求中只有一个固定 marker 字段；用户文本故意请求普通单词 `READY`。如果硬性结构约束有效，输出应受 schema 限制。

- 当前 schema＋流式：3 次全部返回普通文本 `READY`。
- 旧版 `output_format`＋官方旧 beta header：1 次返回 `READY`。
- 当前 schema＋非流式：1 次返回 `READY`。
- `strict: true` 工具＋指定 `tool_choice`：1 次仍返回文本 `READY`，未返回工具调用。
- 以上 6 次均 HTTP 200、`end_turn`，请求与原始响应完整保留。

Anthropic 官方文档将 Haiku 4.5 列为结构化输出支持模型，并给出 `output_config.format` 参数；因此不能把中转接口接受参数但不执行约束等同于官方 API 的相同行为。[官方结构化输出文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

证据：[原始控制实验摘要](probes/summary.json)。失败的旧格式和强制工具方案不能作为已经验证可用的修复建议。

## 3. 相同请求呈现两类行为，system 传递存在不一致迹象

在 215 个有完整响应的候选中：

- 上报非零输入缓存用量的 100 个响应，全部属于非规定 JSON 的 ST/分析文本。
- 未上报输入缓存用量的 115 个响应，都能找到有效的候选 JSON：60 个直接通过格式检查，45 个说明超长，10 个 JSON 块外有说明。
- 发现 24 组 HTTP 请求内容完全相同，但同时出现上述两类响应。首题四组第一次请求的文件哈希完全相同：Full 返回可接受 JSON，Neither 返回说明超长 JSON，NoAssets 和 NoFeedback 返回非 JSON 的 ST/说明。

这不是“缓存导致失败”的因果证明；缓存字段是两类返回行为的可观察标记。证据支持怀疑代理路由或请求包装不同，无法在没有服务端日志的情况下定位到具体上游节点，也不能证明实际底层模型身份。

为排除早期诊断标记词触发拒答的干扰，另做 7 次普通算术对照：用户都问 `2+2`，要求返回 `{"answer":4}`。

- 把格式要求放在 system：3 次字符串形式中仅 1 次返回目标 JSON，另外 2 次返回裸 `4`；system 数组形式 1 次也返回裸 `4`。三次裸数响应均带缓存用量。
- 把同一格式要求放进 user：3 次均返回目标 JSON（带围栏，原有解析器可接受），其中 1 次带缓存用量。

短请求证明把约束放在 user 中有改善迹象，尚不证明长 PLC 请求可稳定遵守，不能据此直接宣称问题已修复。原始诊断响应中还出现 Kiro 自我描述；这只是响应内容，不足以单独证明上游架构或模型身份。

证据：[相同请求的两类响应](mixed_route_evidence.json)、[无诊断标记词的算术对照](neutral_probes/summary.json)。

## 4. 本地门禁把说明文字当作程序正确性的前置条件

`our_method/method_history_feedback/two_level.py:83` 的 `apply_complete` 对 `code`、`change_summary`、`applicability_notes` 一起校验；说明长度分别要求不超过 800、500 字符。任一超长便抛出异常，返回代码之前就失败。

`our_method/method_history_feedback/workflow.py:148` 捕获该异常后，记录一个没有工具检查的失败候选并继续下一次生成。该调用消耗候选次数和 token。即使代码完整、可编译，也没有机会接受测试。下一次请求会收到格式错误文本，但不收到本次被丢弃的新代码；反复重新生成不能保证修复同一程序。

具体例子：NoFeedback 第 4 题第 3 个候选有 5,386 字符的代码，说明字段长 505 字符，因超过上限 5 字符而未进入编译。Neither 第 4 题第 10 个候选的 change_summary 为 807 字符，同样因超过 7 字符被拒。这两个例子仅证明被门禁拒绝，不表示代码本来正确。

这里不是 JSON 解析器把合法 JSON 解错，而是过严的业务准入规则。解析器也并非完全不支持 Markdown：它支持覆盖整个响应的一个 JSON 围栏，不接受围栏前后的分析说明。现有约束在 Qwen 的结构化生成环境里相对容易满足，但迁移到未执行硬约束的代理时，格式能力成为了额外且强烈的测量因素。

此外，Haiku 的 schema 转换移除了服务端不支持的长度边界，但未像官方 SDK 一样把移除的边界补入字段 description。system 里仍有 800/500 字符要求，因此不能说完全没告诉模型；但在 system 传递不稳定时，限制更难起效。这是适配的次要不足，不足以解释纯 ST 而非 JSON 的所有情况。

## 5. 原样代码复测证明存在本可提前成功的候选

对全部 45 个说明超长候选，以及 10 个有唯一候选 JSON 块的响应，抽取原始 JSON 解码后的 `code`，不编辑、不修复、不替换转义字符，交给同一个冻结测试器。代码哈希与所有工具回执绑定；55 次复测单独存放，无新增模型调用，不回填正式成绩。

- 55 份中 25 份通过编译。
- 5 份通过编译和全部运行测试：说明超长 3 份，块外附带说明 2 份。
- 这 5 份分属 4 个任务流：Full 第 2 题、Neither 第 6 题、NoAssets 第 4 题和第 5 题；这些任务后来在正式尝试中也成功了。因此证据直接证明浪费尝试与延迟首次成功，不能把它写成“新增 5 个成功任务”。

例如 Full 第 2 题第 4 次的 code 为 4,967 字符，change_summary 为 915 字符；正式流程只因说明超长拒绝，单独复测的原样代码实际通过。Neither 第 6 题第 1 次 code 为 5,570 字符，change_summary 为 839 字符，也能原样通过。这还会影响首候选成功率的解释。

证据：[复测摘要与逐个回执索引](unchanged_code_recheck/summary.json)。剩余 100 个非 JSON 响应中有多版本、片段和分析文本，未按“任取最后一个代码块”的办法重判，不能假定全部都可无歧义恢复。

## 6. 修正优先级与实验解释

1. 先验证并固定能稳定传递 system 和约束的推理入口；不能再以 HTTP 200 和模型名作为接口兼容性通过条件。对当前代理，短请求显示把完整输出契约放在 user 内可能有效，但须先验证长 PLC 和学习请求。仅换旧版 schema 或强制 tool 已被本次小实验否定。
2. 将 PLC 代码的测试资格与说明文本长度解耦。原始说明完整归档，需要进入后续上下文时再做明确标记的受限展示；代码是否正确由原编译器和测试用例判断。不能伪造“使用过哪些历史经验”的字段。
3. 对唯一、完整且来源明确的 JSON/代码输出建立确定性提取规则；多候选或片段保持拒绝。不得通过猜测、拼接多个方案、替换代码文本来制造通过。
4. 若改动接口或解析协议，应保留本轮全部结果，在新版本中统一四组规则；所有模型调用仍记账。旧成绩不能静默改写，也不能把格式失败重试当作免费尝试。

本次没有修改正式运行代码，也没有停止正在运行的 Haiku。启动前我已看到围栏输出，却只记录了“未验证硬约束”，没有继续验证长请求与 system 行为就启动；该资格检查不充分，属于此次接入工作的遗漏。

诊断共 19 个小模型调用、42,078 个接口上报 token；另有 55 个现成代码的工具复测，0 个额外代码生成。诊断费用与正式实验账本分开。
